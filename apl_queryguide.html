STEP 1 — 문제 쿼리 식별 최우선
현재 시스템이 죽는 시점의 쿼리를 정확히 특정한다. DBA에게 Slow Query 로그 또는 AWR 리포트(Oracle) 요청. 어떤 테이블, 어떤 조건에서 발생하는지 먼저 파악.
STEP 2 — 실행계획(EXPLAIN PLAN) 확인
문제 쿼리에 EXPLAIN PLAN을 돌려 Full Table Scan 여부, 인덱스 미사용 여부를 확인. 비용(Cost)과 행 수(Rows) 예측값을 체크.
STEP 3 — 데이터 볼륨 파악
대상 테이블의 건수, 파티션 구조, 인덱스 현황 확인. 보험 계약 테이블은 수천만 건 이상인 경우가 많음. 파티션이 있다면 파티션 pruning이 되는지 확인.
STEP 4 — 개선안 적용 (인덱스 → 쿼리 튜닝 → 배치 분산 순)
인덱스로 해결 가능한 건 먼저 DBA와 협의. 쿼리 구조 문제라면 리팩토링. 데이터량 자체가 문제라면 배치를 기간/부서 단위로 분산 처리.
STEP 5 — 검증 및 모니터링
개선 전후 실행 시간, CPU/메모리 사용량 비교. 운영 배포 전 반드시 검증 환경에서 충분한 부하 테스트 수행.
첫날 DBA 없이 섣불리 인덱스 생성하거나 쿼리 힌트를 추가하면 오히려 역효과가 날 수 있어요. 반드시 DBA와 먼저 협의 후 진행하는 것을 권장합니다.

Oracle 기준 — 빠른 진단 쿼리
-- 현재 실행 중인 느린 쿼리 확인 SELECT s.sid, s.serial#, s.username, s.status, s.sql_id, t.elapsed_time/1000000 AS elapsed_sec, SUBSTR(q.sql_text, 1, 100) AS sql_text FROM v$session s JOIN v$sqlarea q ON s.sql_id = q.sql_id JOIN v$sql_monitor t ON s.sql_id = t.sql_id WHERE s.status = 'ACTIVE' ORDER BY t.elapsed_time DESC; -- 테이블 건수 및 파티션 현황 확인 SELECT table_name, num_rows, last_analyzed FROM all_tables WHERE owner = 'SCHEMA명' ORDER BY num_rows DESC; -- 인덱스 현황 확인 SELECT index_name, column_name, column_position FROM all_ind_columns WHERE table_name = '테이블명' ORDER BY index_name, column_position;
1 인덱스 전략
배분 배치에서 가장 자주 쓰이는 조건 컬럼(기준년월, 계약상태코드, 부서코드)에 복합 인덱스를 구성합니다. 선택도(Selectivity)가 높은 컬럼을 앞에 배치하는 것이 핵심입니다.
-- 복합 인덱스 생성 예시 (DBA 협의 후 적용) CREATE INDEX idx_contract_ym_status ON tb_contract (base_ym, status_cd, dept_cd); -- 함수 기반 인덱스 (날짜 형변환 처리 시) CREATE INDEX idx_contract_ym_func ON tb_contract (TO_CHAR(contract_dt, 'YYYYMM'));
2 쿼리 튜닝 — 흔한 패턴 개선
-- BAD : IN 절에 서브쿼리 + 대용량 SELECT * FROM tb_contract WHERE contract_no IN (SELECT contract_no FROM tb_payment WHERE base_ym = '202503'); -- GOOD : EXISTS 또는 JOIN으로 변환 SELECT c.* FROM tb_contract c WHERE EXISTS ( SELECT 1 FROM tb_payment p WHERE p.contract_no = c.contract_no AND p.base_ym = '202503' ); -- BAD : SELECT * (불필요한 컬럼 전체 조회) SELECT * FROM tb_contract WHERE base_ym = '202503'; -- GOOD : 필요한 컬럼만 명시 SELECT contract_no, dept_cd, premium_amt FROM tb_contract WHERE base_ym = '202503' AND status_cd = 'ACTIVE';
3 임시 테이블 활용 (중간 집계 분리)
한 번에 전체를 조인·집계하지 않고, 중간 결과를 임시 테이블에 담아 단계별로 처리하면 메모리 부하를 크게 줄일 수 있습니다.
-- 1단계 : 원천 데이터 임시 테이블에 적재 CREATE GLOBAL TEMPORARY TABLE tmp_contract_base ON COMMIT PRESERVE ROWS AS SELECT contract_no, dept_cd, premium_amt FROM tb_contract WHERE base_ym = :baseYm AND status_cd = 'ACTIVE'; -- 2단계 : 임시 테이블 기준으로 집계 (부하 분산) SELECT dept_cd, COUNT(*) AS contract_cnt, SUM(premium_amt) AS total_premium FROM tmp_contract_base GROUP BY dept_cd;
Spring Batch 환경에서는 Tasklet 단위로 각 단계를 분리해 트랜잭션을 작게 유지하는 것이 효과적입니다.
사업비 배분 — 대용량 안전 처리 쿼리 패턴
-- 배분동인 집계 : 파티션 pruning + 필요 컬럼만 조회 SELECT dept_cd, COUNT(*) AS contract_cnt, SUM(premium_amt) AS total_premium, ROUND( COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 6 ) AS alloc_ratio FROM tb_contract -- 파티션 테이블 가정 WHERE base_ym = :baseYm -- 파티션 키 → Pruning 적용 AND status_cd = 'ACTIVE' GROUP BY dept_cd; -- 배분 결과 MERGE (중복 실행 안전 처리) MERGE INTO tb_cost_alloc_result t USING ( SELECT :baseYm AS base_ym, :costItemCd AS cost_item_cd, dept_cd, alloc_ratio, ROUND(:totalAmt * alloc_ratio / 100, 0) AS alloc_amt FROM v_dept_alloc_ratio ) s ON (t.base_ym = s.base_ym AND t.cost_item_cd = s.cost_item_cd AND t.dept_cd = s.dept_cd) WHEN MATCHED THEN UPDATE SET t.alloc_ratio = s.alloc_ratio, t.alloc_amt = s.alloc_amt, t.upd_dt = SYSDATE WHEN NOT MATCHED THEN INSERT (base_ym, cost_item_cd, dept_cd, alloc_ratio, alloc_amt, reg_dt) VALUES (s.base_ym, s.cost_item_cd, s.dept_cd, s.alloc_ratio, s.alloc_amt, SYSDATE);
MERGE 사용 시 배치를 재실행해도 중복 데이터 없이 안전하게 처리됩니다. INSERT + DELETE보다 훨씬 안전해요.
합계 검증 쿼리 (배분 후 반드시 실행)
-- 배분 전 원천 합계와 배분 후 합계 일치 여부 검증 SELECT '원천합계' AS gubun, SUM(cost_amt) AS total_amt FROM tb_cost_source WHERE base_ym = :baseYm UNION ALL SELECT '배분결과합계' AS gubun, SUM(alloc_amt) AS total_amt FROM tb_cost_alloc_result WHERE base_ym = :baseYm;
배치 분산 처리 전략 — 데이터량이 근본 문제일 때
인덱스·튜닝으로도 해결이 안 될 만큼 데이터량이 많다면, 배치 자체를 나누는 것이 가장 확실한 방법입니다.
분산 방식적용 상황효과
기간 분할
월 → 주 또는 일 단위		 기준년월 1개월치를 한 번에 처리할 때 죽는 경우 처리 건수를 1/4~1/30로 줄임
부서/조직 분할 전사 부서를 한 번에 집계할 때 부하 과다 병렬 실행 또는 순차 분할 처리 가능
청크(Chunk) 분할 Spring Batch 환경에서 대용량 INSERT 트랜잭션 단위를 작게 유지 (1000건 단위 권장)
야간 배치 스케줄링 업무시간 중 시스템 부하 문제 업무 피크타임 회피, 리소스 독점 가능
Spring Batch Chunk 분산 처리 예제
// 1000건 단위 청크 처리 — 메모리 부하 최소화 @Bean public Step allocationStep(StepBuilderFactory factory) { return factory.get("allocationStep") .<ContractData, AllocResult>chunk(1000) // 1000건씩 커밋 .reader(contractItemReader()) .processor(allocationProcessor()) .writer(allocResultWriter()) .faultTolerant() .retryLimit(3) // 오류 시 3회 재시도 .retry(Exception.class) .build(); } // 기간 파라미터로 월별 분할 실행 @Bean public JdbcPagingItemReader<ContractData> contractItemReader() { Map<String, Object> params = new HashMap<>(); params.put("baseYm", jobParameters.getString("baseYm")); return new JdbcPagingItemReaderBuilder<ContractData>() .name("contractReader") .dataSource(dataSource) .selectClause("SELECT contract_no, dept_cd, premium_amt") .fromClause("FROM tb_contract") .whereClause("WHERE base_ym = :baseYm AND status_cd = 'ACTIVE'") .sortKeys(Map.of("contract_no", Order.ASCENDING)) .parameterValues(params) .pageSize(1000) .rowMapper(new BeanPropertyRowMapper<>(ContractData.class)) .build(); }
JdbcPagingItemReader는 대용량 데이터를 페이지 단위로 읽어오기 때문에 전체 ResultSet을 메모리에 올리지 않아요. 보험사 대용량 환경에서 가장 안전한 패턴입니다.
